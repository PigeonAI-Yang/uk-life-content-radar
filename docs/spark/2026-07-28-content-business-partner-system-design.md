# 内容事业合伙人系统设计

状态：待用户复核
日期：2026-07-28
适用项目：自媒体桌面终端

## 1. 背景

自媒体桌面终端不能只被理解为一套需要用户逐页操作的软件，也不能只依赖一份讲解按钮和基础命令的操作 Skill。

目标形态由三部分共同组成：

1. Skill：提供经营方法、判断原则与协作规则；
2. 应用终端：保存真实业务状态与长期内容资产；
3. 外部 Agent（Codex）：基于当前事实进行动态判断并完成执行。

三者组合后，用户不必亲自管理每一个操作步骤，而是以业务负责人身份确定方向、批准战略和最终发布。Codex 作为内容事业合伙人，使用终端持续经营用户的内容业务。

## 2. 已确认的愿景

完整系统的愿景是：

> 由用户领导、Codex 执行，以 Skill 提供经营方法、以终端保存业务事实的个人内容商业经营系统。

系统不是单纯追求内容数量、流量或基础自动化，而是以用户自有产品和服务的商业结果为最高目标，通过内容持续建立信任、获得目标客户并推动收入。

## 3. 已确认的产品目标

### 3.1 合伙人身份

总控 Skill 的角色是“内容事业合伙人”，而不是软件操作员、写作助手或任务路由器。

它必须：

- 理解用户为什么经营账号以及希望获得什么商业结果；
- 从产品、目标客户和客户需求倒推内容工作；
- 判断当前最重要的商业问题，而不是等待用户逐项派发操作；
- 组织研究、选题、内容、素材、多平台适配、发布准备与复盘；
- 让资料、洞察、内容和经营反馈成为可持续复用的长期资产；
- 主动挑战假设并提出策略调整，但不越过用户的战略主权。

### 3.2 商业结果优先

最高目标是通过内容销售用户自己的产品或服务。

默认经营链为：

> 产品与服务 → 目标客户 → 客户问题与购买动机 → 信任建设 → 内容与行动引导 → 咨询与成交反馈 → 策略调整

流量、内容数量和资料规模属于过程指标。它们只有在支持目标客户、信任、咨询或收入时才具有经营价值。

### 3.3 完整商业闭环

内容事业合伙人负责理解完整商业闭环：

- 产品与服务；
- 目标客户；
- 客户问题、需求和异议；
- 内容策略与账号定位；
- 研究、选题和生产；
- 多平台分发准备；
- 咨询与成交反馈；
- 基于真实结果的经营复盘。

Codex 不替用户完成资金行为或最终成交，但必须理解真实咨询和成交反馈，才能判断内容是否有效。

### 3.4 主动经营

当用户只说“开始工作”时，总控 Skill 应当：

1. 读取终端中的业务现状；
2. 找出当前最重要的商业问题或约束；
3. 提出本轮目标与判断依据；
4. 在既定战略范围内主动执行；
5. 仅在战略选择、缺失关键事实和最终发布时请求用户决策；
6. 将过程与结果写回终端，形成下一轮可延续状态。

不得凭空编造价格、客户反馈、成交数据或其他商业事实。缺少关键事实时必须明确向用户索取。

## 4. 已确认的系统架构

采用“总控 Skill + 专业子 Skill + 应用终端 + 外部 Codex”的组合，而不是单一超级 Skill，也不把所有经营判断固化进应用代码。

### 4.1 用户

用户拥有以下主权：

- 决定卖什么；
- 决定服务谁；
- 批准账号定位与正式经营策略；
- 批准产品、价格和转化路径的重大变化；
- 批准最终发布包。

### 4.2 总控 Skill

总控 Skill 负责：

- 读取和理解商业现状；
- 诊断经营瓶颈；
- 确定阶段目标和下一最佳行动；
- 选择并编排专业子 Skill；
- 检查专业结果是否服务商业目标；
- 要求 Codex 将经营结果写回终端；
- 在越过授权边界前请求用户批准。

总控 Skill 必须拥有完整的经营判断方法，不能退化为只按关键词转发任务的路由器。

### 4.3 专业子 Skill

专业子 Skill 提供某一环节的专业能力，例如：

- 英国生活资讯研究与事实核验；
- 产品与客户研究；
- 选题策划；
- 平台文案创作；
- 图片与封面制作；
- 发布包准备；
- 商业反馈复盘。

专业子 Skill 对本环节的质量负责，但不能自行改变正式商业策略。

### 4.4 外部 Agent（Codex）

Codex 负责：

- 加载总控 Skill；
- 读取终端中的当前业务事实；
- 进行情境化推理；
- 调用专业子 Skill；
- 通过 MCP 操作终端；
- 完成写后读回；
- 把结果、失败、证据和待决策项反馈给用户；
- 把本轮经营状态写回终端。

Codex 的聊天上下文不是正式、长期的经营记忆。

### 4.5 应用终端

终端是唯一可核验的业务账本，保存：

- 账号、资料、摘录、内容、素材、版本、发布包和任务；
- 产品与服务；
- 目标客户；
- 客户问题、需求和异议；
- 转化目标；
- 咨询与成交反馈；
- 策略版本、批准记录和经营决策；
- 真实文件、对象关系、执行状态和错误。

Skill 不硬编码用户的动态业务事实。个人策略和经营反馈必须进入终端，确保更换 Codex 会话或未来更换 Agent 后仍可延续。

## 5. 已确认的主权边界

- Codex 可以主动诊断、研究、规划和执行既定战略内的工作。
- Codex 可以提出账号定位、产品、价格或转化路径的调整建议。
- 未经用户批准，建议不能写成正式经营策略。
- 最终发布批准只能由用户完成。
- 专业子 Skill 不得自行提升权限或绕过总控 Skill 的经营约束。
- 每轮工作必须在终端产生可读回的业务状态，不能只产生聊天回复。

## 6. 已确认的设计原则

1. 商业结果优先于内容数量和表面流量。
2. 主动经营优先于等待逐项指令。
3. 终端事实优先于聊天记忆和模型推测。
4. 长期资产积累必须服务真实经营，而不是为了堆积资料。
5. 执行可以高度自主，战略变化必须人工批准。
6. 总控 Skill 负责经营判断，专业 Skill 负责环节质量。
7. UI 与 MCP 必须继续调用同一业务内核并操作同一份数据。
8. 用户保留最终方向、策略与发布主权。

## 7. 主要商业链路

第一条必须跑通的商业链路是：

> 小红书帖子 → 私信咨询 → 微信私域 → 洽谈 → 成交 → 结果反哺下一轮内容

终端必须能够从一篇帖子看到它带来的客户，也能从一个客户反查最初来自哪篇内容。

| 环节 | 必须保存的事实 |
| --- | --- |
| 帖子 | 平台、账号、内容版本、发布时间、标题、图片和行动引导 |
| 平台表现 | 曝光、阅读、点赞、收藏、评论和记录时间 |
| 私信 | 来源帖子、咨询内容、首次咨询时间和当前意向 |
| 微信 | 是否添加、添加时间、当前关系和下一步 |
| 洽谈 | 客户需求、产品匹配、报价、顾虑和跟进时间 |
| 结果 | 成交产品、金额、时间，或未成交原因 |
| 内容关系 | 哪个选题、标题、正文和引导带来了哪些咨询与成交 |

平台表现、私信和微信材料第一版采用混合录入：

- 用户提供截图、复制文本或口述事实；
- Codex 提取结构化信息并通过 MCP 写入终端；
- 终端保存原始文件、提取结果和对象关系；
- 用户确认身份、成交金额、正式报价等关键事实；
- 暂不依赖小红书或微信开放接口，不模拟登录或自动操作平台。

## 8. 账号定位与内容范围

账号的上层定位是：

> 面向在英华人的实用资讯、生活指南与可信服务入口。

租房材料等产品是商业服务，但不等于账号的全部内容。商业关联发生在整个账号层面，不要求每篇资讯都插入产品广告。

### 8.1 长期资料来源

内容雷达持续关注：

- 签证、移民和身份政策；
- 留学生政策、学费、毕业与求职；
- 工作、工资、税务和劳动权益；
- 租房、押金、担保人和住房政策；
- 银行、转账、信用和诈骗提醒；
- 交通变化、罢工、票价和出行；
- 水电燃气、通信、地方税和生活账单；
- NHS、看病和保险；
- 超市、餐饮、出行折扣和实用优惠；
- 免费活动和其他值得分享的省钱机会；
- 英国新闻对在英华人的实际影响；
- 专业人士解释、华人社区讨论和真实生活经验；
- 私信、微信沟通、成交过程和用户自己的判断。

一条信息是否值得进入创作候选，先看：

1. 是否影响在英华人的生活、利益或决定；
2. 是否有时效性，什么时候过期；
3. 是否容易被错过或误解；
4. 是否有可靠来源；
5. 账号能否比简单转发多解释一步；
6. 用户看完能否采取有用行动。

### 8.2 内容组合

内容至少包含：

- 及时消息：新闻、政策变化、交通中断、折扣和突发提醒；
- 长期实用内容：租房、签证、工作、银行和账单指南；
- 判断与信任内容：政策影响、常见误区、经验、案例和做事方式；
- 服务相关内容：针对明确困难和高意向需求，介绍解决办法与服务。

流量内容负责让目标人群看到账号；实用和判断内容负责形成长期信任；服务内容负责推动真实咨询。具体比例不写死，由实际发布和咨询结果调整。

## 9. 素材聚合与创作

终端不是收藏夹。每份材料进入后都必须保留原件、出处和时间，并整理成可创作的信息：

- 发生了什么；
- 影响哪些人；
- 哪些事实已经确认；
- 哪些地方容易被误解；
- 普通人会遇到什么实际问题；
- 可以形成哪些选题；
- 还缺什么案例、图片或证据；
- 是否与已有资料或内容重复；
- 是否需要在某个时间前发布。

私信和微信沟通除了属于客户记录，也可以提取客户使用的真实说法、反复出现的问题、购买顾虑和匿名案例，作为新的内容线索。

一次正式创作按以下顺序完成：

1. 明确这篇内容帮助谁、解决什么问题；
2. 读取相关资料、客户说法、历史内容和产品信息；
3. 核对事实与来源，不把推测写成结论；
4. 选择切入角度，避免简单拼接和重复旧文；
5. 形成标题、封面、正文结构和自然的行动引导；
6. 写出公共底稿；
7. 分别适配小红书、抖音图文和微信公众号；
8. 检查是否自然、可信、有用、符合用户表达且不过度销售；
9. 准备图片和发布包；
10. 交给用户最终判断与批准。

终端维护一张可读的创作全貌，持续发现哪些客户问题已经讲过、哪些尚未覆盖、哪些旧文需要更新、哪些高意向问题缺少证据，以及近期内容是否过于重复。

## 10. 主动工作方式

用户在当前 Codex 对话中调用总控 Skill，并可以像与合伙人交流一样说“开始工作”或直接提供材料。用户不需要记忆软件命令、MCP 工具名或专业子 Skill 名称。

每次启动后，Codex：

1. 连接终端并读取已经批准的产品、账号、目标客户、内容历史、客户情况、成交结果、待处理事项和上次进度；
2. 判断现在最值得处理的是信息时效、创作供给、帖子流量、私信、微信沟通、洽谈还是数据缺口；
3. 在既定策略范围内选择一个清楚、可检查的本轮目标；
4. 调用所需专业 Skill 并通过 MCP 执行；
5. 把材料、判断、产物、关系、失败和下一步写回终端；
6. 完成写后读回；
7. 只把需要用户拍板、补充事实或最终批准的事项带回对话。

判断哪一步需要优先处理时使用自然语言：

- 帖子没人看：先检查选题、标题、封面和平台需求；
- 有人看但没人私信：检查内容是否击中真实困难，咨询理由是否自然；
- 有私信但加不上微信：检查首次回复、需求判断和提出加微信的时机；
- 加了微信但聊不下去：检查信任、案例和对客户情况的理解；
- 聊了很多但不成交：检查客户是否准确、产品是否匹配、价格如何解释以及客户在顾虑什么；
- 已经成交但不知道从哪里来：先补全帖子、客户和成交关系；
- 没有足够事实：设计一次小范围尝试，不凭感觉编结论。

每轮只需说清楚：

- 现在卡在哪里；
- 为什么这样判断；
- 这次准备做什么；
- 希望看到什么变化；
- 多久后回来检查；
- 哪些事情需要用户拍板。

## 11. 两个协同空间

Codex 对话和应用终端共同组成工作环境：

| 空间 | 职责 |
| --- | --- |
| Codex 对话 | 表达意图、共同思考、作出判断、提供截图和临时信息 |
| 应用终端 | 聚合资料、客户、内容、素材、沟通、成交和真实文件，保存关系与进度 |

总控 Skill 必须遵守：

> 任何会影响后续经营的事实、决定、材料和产物，都不能只停留在聊天里；必须通过 MCP 进入终端，并完成读回确认。

收到外部材料时统一执行：

> 收到材料 → 判断是什么 → 保存原件 → 建立或更新业务对象 → 关联上下文 → 更新状态 → 形成下一步 → 读回确认

终端既不是要求用户逐页完成流程的传统软件，也不是隐藏数据库。它是用户和 Codex 共同使用的内容生意工作台。

## 12. 最小经营对象

第一版只增加支撑真实链路的对象，不建设通用 CRM。

### 12.1 产品或服务

- 名称；
- 目标客户；
- 解决的问题；
- 价格或价格范围；
- 服务范围；
- 适合与不适合的人；
- 当前批准版本。

### 12.2 客户线索

- 昵称或代称；
- 来源账号、平台和帖子；
- 首次咨询时间；
- 核心需求与当前意向；
- 是否添加微信；
- 当前阶段；
- 下一步行动。

阶段保持简单：

> 新私信 → 已了解需求 → 已加微信 → 洽谈中 → 已成交 / 未成交

### 12.3 沟通记录

- 私信、微信或用户口述；
- 原始截图或文本文件；
- Codex 提取的需求、问题和顾虑；
- 已发送或建议发送的回应；
- 本次结论；
- 下次跟进时间；
- 用户确认状态。

### 12.4 成交结果

- 对应客户和产品；
- 成交金额与时间；
- 未成交原因；
- 最初来源帖子；
- 关键内容和沟通；
- 可以反哺下一轮创作的客户洞察。

## 13. “经营”工作区

终端增加一个“经营”一级工作区，集中回答：

1. 最近哪些帖子带来了咨询；
2. 现在有哪些客户正在谈；
3. 今天有哪些人需要跟进；
4. 哪些客户成交或没有成交，为什么；
5. 接下来最值得做什么内容。

工作区包含：

- 当前生意：已批准的产品、重点客户、账号目标和正在验证的想法；
- 从帖子到成交：帖子、私信、微信、洽谈和结果的真实关系；
- 今天要处理：新私信、待确认提取结果、客户跟进、策略提案和待批准发布包；
- 客户与沟通：来源、需求、进度、顾虑、下一步和原始记录；
- 经营回看：哪些内容带来咨询、哪些客户成交、最近反复出现什么需求，以及下一轮应继续或停止什么。

不分别增加“产品”“客户”“成交”等大量一级导航，不把终端做成传统企业管理软件。

## 14. 总控 Skill 与专业 Skill

采用一个总控 Skill 编排多个专业 Skill。

总控 Skill 负责：

- 理解当前商业目标；
- 判断优先事项；
- 选择合适的专业能力；
- 提供本轮所需业务上下文；
- 验收专业结果是否服务本轮目标；
- 要求结果进入终端；
- 处理专业 Skill 之间的交接；
- 在越过授权边界前请求用户批准。

首批专业能力包括：

- 英国生活资讯发现与事实核验；
- 资料整理与研究包；
- 选题判断；
- 平台文案创作；
- 图片与封面；
- 发布包准备；
- 私信和微信材料整理；
- 客户沟通建议；
- 内容与成交结果回看。

用户通常只调用总控 Skill。总控 Skill 不能只根据关键词转发任务；它必须明确本轮目标、输入事实、需要的专业结果和验收标准。

专业 Skill 的结果不能只是一段聊天文字。只要会影响后续工作，就必须返回终端对象、真实文件或状态读回。

## 15. 学习用户的判断与表达

总控 Skill 通过用户的真实选择逐渐理解用户，但不能把一次随口意见自动升级成永久规则。

终端保存：

- 已批准的账号定位和策略版本；
- 已批准与被拒绝的选题及原因；
- 用户修改前后的内容版本；
- 用户认可的标题、表达、案例和图片；
- 禁止使用的表达；
- 产品、报价和服务边界；
- 用户确认的客户判断；
- 阶段复盘结论。

Codex 可以从历史决定中提出稳定偏好，但只有用户确认后才能成为正式规则。换一个会话或 Agent 时，以终端中的已批准事实为准，不依赖旧聊天窗口。

语言统一使用自然、直接的中文：

- 像一起做生意的合伙人，不像咨询报告；
- 默认先讲结论和下一步，再补原因与数据；
- 能说“帖子没人看”，就不说“公域触达不足”；
- 能说“加了微信但没成交”，就不说生硬的英文直译术语；
- 专业概念只有在能帮助用户作决定时才出现。

## 16. 定时信息收集

采用“定时扫描 + 对话决策”：

- 后台每天扫描、保存、去重、初步核验并标明时效；
- 后台只形成候选信息，不自动决定正式选题，不自动发布；
- 用户调用总控 Skill并说“开始工作”后，Codex 读取最新候选；
- Codex 判断哪些需要尽快讲、哪些值得深入研究、哪些进入长期选题库、哪些不值得占用发布位置；
- 正式创作、批准与发布继续在当前对话和终端中完成。

后台扫描失败时保留上次成功时间和明确错误，不把旧信息描述成当天新发现。

## 17. 首次使用

首次不要求填写复杂商业问卷，只建立最小底账：

1. 当前销售什么产品或服务；
2. 哪类人最可能付费；
3. 客户通常因为什么来咨询；
4. 当前价格和服务过程；
5. 最近几个真实咨询或成交案例。

完成最小建档后立即开始真实工作。后续从新的私信、微信沟通和成交结果中持续补充客户说法、常见困难、购买顾虑和成功原因。

## 18. 批准与策略版本

以下变化必须形成经营提案并由用户批准：

- 产品或服务范围；
- 目标客户；
- 账号定位；
- 正式价格；
- 关键服务承诺；
- 主要转化方式；
- 将一次观察提升为长期经营规则。

提案至少说明：

- 建议改变什么；
- 依据哪些真实材料；
- 希望解决什么问题；
- 可能带来什么影响；
- 如何判断改变是否有效。

批准后生成新的正式策略版本。旧内容和历史决定仍保留，不覆盖。最终发布批准继续遵守正文、图片顺序、账号、平台和模板版本绑定规则。

## 19. 失败与信息不足

- MCP 无法连接：停止写入，报告连接状态和未执行事项，不用聊天回复冒充已保存；
- 原始文件保存失败：对象不得标记完成；
- 截图或对话无法确认属于谁：进入待确认状态，不随意合并客户；
- 关键信息缺失：只询问会改变决定的最少问题；
- 来源无法核验：标明未核验，不作为确定事实发布；
- 专业 Skill 不可用：说明缺少哪一段能力，完成仍可安全完成的部分；
- 定时扫描部分失败：保留每个来源的成功与失败，不把部分成功写成全部完成；
- 用户中断：保存已完成对象和剩余步骤，下次从终端继续；
- 策略与新证据冲突：提交提案，不擅自改写正式策略；
- 平台数据或成交信息不足：承认无法判断，不编造效果。

## 20. 验收标准

总控 Skill 与终端的完整形态至少满足以下可证伪要求：

1. 用户在新 Codex 会话中调用总控 Skill并说“开始工作”，Codex 能从终端恢复上次经营状态；
2. 用户提供一张私信或微信截图后，原件、客户、沟通、来源帖子和下一步均可从终端读回；
3. 一条外部资讯从原始来源进入资料、选题、内容和发布包，全程保留关系与文件；
4. 一篇已发布帖子能够关联平台表现、私信、微信客户和成交结果；
5. Codex 能根据真实链路说明现在卡在哪一步，并提出一个可检查的下一步；
6. 没有足够数据时，Codex 明确说无法判断，并提出最小尝试；
7. 专业 Skill 的产物写入终端，不只停留在聊天；
8. 产品、价格、受众或账号定位变化未经用户批准不能成为正式策略；
9. 正文、图片、账号或配置变化后旧发布批准失效；
10. 定时扫描失败时能看到最后成功时间、失败来源和错误；
11. 换一个 Codex 会话后不依赖旧聊天记录仍可继续；
12. 用户可以在“经营”工作区核对从帖子到成交的真实关系；
13. 对话、终端数据库和磁盘文件对同一对象的状态一致；
14. 全部用户可见文字和 Skill 输出使用自然中文，不以英文直译术语代替清楚表达。

## 21. 实施边界

本设计描述终极协作形态，但实施必须分阶段完成：

1. 先补终端的产品、客户、沟通、成交和关系能力；
2. 再通过 MCP 暴露同语义业务命令和查询；
3. 再实现总控 Skill，以真实终端能力为依据；
4. 再接入专业 Skill 和定时扫描；
5. 最后以真实内容、真实截图、真实客户链路和跨会话读回验收。

不得先写一份声称“能够经营”的总控 Skill，却用不存在的终端能力或模拟数据冒充闭环。
