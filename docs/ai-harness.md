# AI（人工智能）开发 harness（验证脚手架）

## 目标

本 harness（验证脚手架）让后续智能体在业务代码出现前就能区分已确认产品契约、当前项目事实和工程建议，并在修改后留下可重复验证的证据。

## 产物地图

| 产物 | 作用 |
| --- | --- |
| `AGENTS.md` | 所有任务的入口规则与文档索引 |
| `docs/architecture.md` | 当前真实结构、边界和未知项 |
| `docs/development-workflow.md` | 修改与报告流程 |
| `docs/verification.md` | 可运行命令与验证缺口 |
| `.ai/evals/README.md` | 功能验收与回归模板 |
| `scripts/check.ps1` | 一条命令执行当前硬检查 |

## 规则来源标准

每条强规则必须属于以下一种：

- 项目事实：从当前文件、配置、源码、测试或运行结果观察得到。
- 用户要求：来自用户明确确认的产品目标或边界。
- 建议：工程判断，必须明确标注，技术事实变化后可调整。

没有证据时记录未知项，不把推测写成项目规则。

## 软规则与硬检查

- 产品边界、工作方法和停止条件写入 `AGENTS.md` 与文档。
- 可机械验证的目录、关键文档和契约标题由 `scripts/check.ps1` 检查。
- 应用技术栈落地后，把类型检查、代码检查、测试、构建和关键业务验收接入同一脚本。

## 更新策略

以下情况必须更新 harness（验证脚手架）：

- 技术栈、包管理器、源码入口或构建方式确定。
- 新增可重复的失败模式或验收命令。
- PRD（产品需求文档）边界经用户确认发生变化。
- 某条文字规则可以转成确定性检查。

一次性事故只记录在任务报告；重复出现并能形成通用约束后，才进入 harness（验证脚手架）。
