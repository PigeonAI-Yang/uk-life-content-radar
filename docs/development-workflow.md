# 开发流程

## 修改前

1. 阅读 `AGENTS.md` 及其为当前任务指定的文档。
2. 检查当前目录、版本库状态、依赖清单、入口和现有检查。
3. 区分项目事实、用户要求、建议和未知项。
4. BUG（缺陷）任务先设计最小可证伪实验并稳定复现。
5. 说明最小修改位置、原因和验收标准。

## 修改中

- 从“不做、复用、标准库、平台原生、已有依赖、最小实现”的顺序选择方案。
- 只改当前契约要求的最少文件。
- 保留用户已有文件和无关改动，不覆盖未确认内容。
- 非平凡分支、解析、状态转换或文件写入至少留下一个可运行检查。
- 业务界面能力必须同步考虑 API（应用程序接口）与 MCP（模型上下文协议）的等价入口。
- 不把临时可视化原型当成应用实现或验收证据。

## 错误处理

- 保留确定的错误传播，不把部分成功报告为整体成功。
- 文件写入、图片处理、发布包生成和长任务失败时，不得留下“已完成”状态。
- 无法复现、根因不明或缺少产品决策时停止猜测性修改，报告阻塞。
- 需要新增依赖、改变 PRD（产品需求文档）范围、删除数据或扩展平台时，先获得用户确认。

## 验证

1. 运行 `pwsh -NoProfile -File scripts/check.ps1`。
2. 若应用项目已存在，再运行 `docs/verification.md` 中记录的类型、代码检查、测试和构建命令。
3. 按风险执行人工主链或功能评测。
4. 保存命令、结果和未执行原因。

## 最终回复

- 先给出完成状态。
- 列出关键改动与验证结果。
- 明确任何失败、跳过、降级、假设和外部阻塞。
- 不以文件创建、命令退出成功或界面截图替代产品验收。

## 必须停下询问的情况

- 产品目标或第一版边界会因选择不同而实质变化。
- 需要不可恢复删除、覆盖用户数据或改变用户指定存储位置。
- 需要新增依赖但现有契约没有授权。
- 现有规则互相冲突且无法从当前证据裁决。
